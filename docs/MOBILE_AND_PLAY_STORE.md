# Larimar — Mobile and Google Play

**What this covers:** the app is now an installable PWA and is packaged for
Google Play as a Trusted Web Activity. This document explains what was built, how
to produce an Android build, and — most importantly — what stands between that
build and a public listing.

---

## 0. Read this before you submit anything

> ### The engineering is ready. The app is not publishable.
>
> **Google Play's Financial Services policy** applies to any app that facilitates
> or appears to facilitate money transfer, remittance, or currency exchange.
> Larimar presents as exactly that — deliberately, because it is a demonstration
> of exactly that.
>
> Submitting it to a **production** track would mean declaring a financial
> service you are not licensed to provide. The realistic outcomes are rejection,
> removal, or developer-account suspension. Account-level enforcement is not
> recoverable by fixing the app.
>
> **What you can legitimately do today:** build the app, and distribute it on an
> **internal testing** or **closed testing** track to a named list of testers.
> Those tracks exist for exactly this — showing a working build to a small,
> known audience.
>
> **What gates a production release** is the same thing that gates everything
> else in this project: the licensing question in
> [`LEGAL_AND_COMPLIANCE.md`](./LEGAL_AND_COMPLIANCE.md). Play's declaration
> asks for proof of registration or licensing in each country you target. There
> is nothing to attach until that exists.

This is not a technical limitation to route around. It is the correct outcome for
an unlicensed financial product, and the packaging below is deliberately built so
it is ready the day the licensing is not hypothetical.

## 1. What was built

### Progressive Web App

| Piece | Where | Notes |
| --- | --- | --- |
| Web app manifest | `src/app/manifest.ts` | Served at `/manifest.webmanifest`. Standalone display, portrait, brand theme. |
| Icons | `public/icons/*.png` | 32 → 512px plus two maskable. Generated by `npm run icons`. |
| Service worker | `public/sw.js` | Offline shell only. See §2 — this is the security-relevant part. |
| Offline page | `public/offline.html` | Static, self-contained, and still says it is a demo. |
| Registration | `src/components/layout/ServiceWorkerRegistrar.tsx` | Production only; dev registration serves stale shells and wastes hours. |

**`display: standalone`, not `fullscreen`.** The traveler is standing at a bank
counter reading a code aloud. Hiding the status bar takes away the clock and the
battery indicator for no benefit.

**`start_url: /dashboard`.** An installed app is opened by someone who already has
an account; the marketing landing page is not what they want from a home-screen
icon.

**Icons are generated, not hand-drawn.** `scripts/generate-icons.ts` renders the
brand mark into an RGBA buffer and encodes PNGs with Node's built-in `zlib`. PNG
is simple enough that a correct encoder is about sixty lines, and it keeps a
native image dependency out of the toolchain. Re-run `npm run icons` after any
brand change.

### Android packaging

| Piece | Where |
| --- | --- |
| Bubblewrap config | `android/twa-manifest.json` |
| Digital Asset Links | `src/app/.well-known/assetlinks.json/route.ts` |
| Signing-material guard | `android/.gitignore` |

## 2. The service worker is deliberately almost useless

This is the part worth reading carefully.

Standard PWA advice is to cache API responses for offline speed. **Here that
would be a security defect.** A service worker cache is durable client-side
storage, readable by any script that later runs on this origin, surviving browser
restarts. This application's API returns transaction records, customer data, and
— on exactly one endpoint — a **live pickup code**, which is a bearer credential
for cash.

So the worker follows four rules:

1. **Never touch `/api/*`.** Those requests pass straight through, uncached and
   untouched.
2. **Never cache an HTML document.** Every page is server-rendered per session; a
   cached dashboard on a shared phone is a data leak.
3. **Cache only immutable, non-personal static assets** — hashed build output and
   brand icons.
4. **Serve a static offline notice** when navigation fails, and nothing more.

The value delivered is installability and a graceful offline message. That is the
correct amount of offline capability for a product where every meaningful action
requires the server anyway — you cannot issue a pickup code offline, and pretending
otherwise would be worse than useless.

Two E2E tests in `tests/e2e/pwa.spec.ts` enforce this: one asserts the cache
contains only allowlisted static paths after browsing, and one runs a complete
transaction to an issued pickup code and then asserts that code appears **nowhere**
in any cache entry.

### One trap worth naming

The service worker would not register, and the browser reported only:

```
An unknown error occurred when fetching the script.
```

Cause: the CSP on a worker script's *own response* governs the worker's execution
context. `sw.js` was being served through middleware with
`script-src 'nonce-…' 'strict-dynamic'`, and the script carries no nonce, so it
was blocked. `sw.js` is now excluded from the middleware matcher. The error
message gives you nothing, so it is recorded here.

## 3. Building the Android app

### Prerequisites

- **A deployed HTTPS domain.** TWA verification fetches
  `https://<domain>/.well-known/assetlinks.json`. `localhost` will not do.
- **JDK 17** and the Android SDK (Bubblewrap can install both).
- **A Google Play Developer account** ($25, one-off).

### Steps

**1. Deploy, and confirm the PWA is live**

```bash
curl -s https://your-domain/manifest.webmanifest | head
curl -s -o /dev/null -w '%{http_code}\n' https://your-domain/sw.js
```

**2. Point the config at your domain**

Edit `android/twa-manifest.json`: replace every `larimar.example.com` with your
host, and set a `packageId` you control (reverse-DNS of a domain you own).

**3. Generate the Android project**

```bash
npm run twa:init
```

Bubblewrap fetches the manifest and icons from your live domain and scaffolds the
project. It will offer to create a signing keystore — **back it up immediately**.
Losing the upload key means you can never update the app; leaking it means someone
else can publish as you.

**4. Build**

```bash
npm run twa:build
```

Produces `app-release-bundle.aab` for Play, and an APK for local testing.

**5. Create the app in Play Console and upload to internal testing**

Do **not** target a production track. See §0.

**6. Wire up Digital Asset Links**

After the first upload, take the fingerprint from **Play Console → Setup → App
integrity → App signing key certificate**, and set:

```
ANDROID_PACKAGE_NAME=com.yourdomain.larimar
ANDROID_SHA256_FINGERPRINT=AB:CD:…:EF
```

Redeploy, then verify:

```bash
curl -s https://your-domain/.well-known/assetlinks.json
```

> **Use the Play App Signing certificate, not your local upload key.** Play
> re-signs your bundle, so the certificate the device sees is Play's, not yours.
> Using the upload key is the single most common reason a TWA ships with a
> visible browser URL bar. The endpoint accepts a comma-separated list, so you
> can trust both during a migration.

Unset, that endpoint returns **404** rather than a placeholder. A placeholder
would be served in production and fail verification while looking configured,
which is worse than nothing.

## 4. Play Console declarations

Every one of these must be answered truthfully. Several have no acceptable answer
today, which is the point of §0.

| Declaration | Position |
| --- | --- |
| **Financial features** | The app presents money transfer / currency exchange. It must be declared. |
| **Financial services licence** | **None exists.** This is the blocker. |
| **Target countries** | Each country's declaration has its own evidence requirements. |
| **Data safety** | Collects email, name, identity-document metadata, transaction history, device and IP data. Encrypted in transit. Not sold. See [`legal/privacy`](../src/content/legal.ts). |
| **Account deletion** | Play requires an in-app and a web deletion path. **Not implemented** — see §6. |
| **Content rating** | IARC questionnaire; declare the simulated financial content. |
| **Ads** | None. |
| **Target audience** | 18+. The product is not for children, and KYC assumes adults. |
| **Privacy policy URL** | `https://your-domain/legal/privacy` — live and reachable. |

### Store listing copy

The listing must not overclaim any more than the app does. Suggested short
description:

> Demonstration of a cash-pickup platform for travelers in the Dominican
> Republic. Not a licensed financial service. No real money is processed.

Do not use screenshots that imply a real transaction with a real institution.
Every location in this build is fictional and labelled as such.

## 5. iOS

Not packaged. The manifest, icons, `apple-touch-icon`, and
`apple-mobile-web-app-*` metadata mean it installs cleanly from Safari via
**Share → Add to Home Screen**, which is the whole of what iOS offers a PWA.

The App Store does not accept web wrappers as readily as Play accepts TWAs;
Guideline 4.2 (minimum functionality) is a real risk for a wrapped web app. A
native or Capacitor shell would be the route, and the same licensing gate applies
first, so it is not worth building yet.

---

## 6. Gaps before any store release

| Gap | Why it matters |
| --- | --- |
| **Licensing** | §0. Everything else is subordinate. |
| **Account deletion flow** | Play *requires* in-app and web deletion paths. Not implemented. Note that financial and audit records are typically subject to statutory retention that overrides a deletion request — the flow must delete what it may and explain what it must keep. |
| **Push notifications** | `enableNotifications: false`. The notification architecture exists server-side but no transport delivers anything. |
| **Crash and ANR reporting** | Play surfaces vitals; nothing is wired up. |
| **Deep links** | The TWA handles in-scope URLs once asset links verify, but no app-specific intent filters exist. |
| **Offline depth** | By design, near zero. See §2. |
| **Play billing** | Not applicable — no digital goods are sold. Worth knowing the policy exists. |

## 7. Local verification

```bash
npm run icons            # regenerate launcher icons from the brand mark
npm run build && npm start
npm run test:e2e -- tests/e2e/pwa.spec.ts
```

The PWA suite checks manifest validity, that every declared icon is a real PNG
(verified by file signature, not by content-type header), that `sw.js` is served
without a blocking CSP, and the two cache-hygiene properties in §2.

Chrome DevTools → **Application** → **Manifest** / **Service Workers** shows the
install prompt criteria and the active worker.

> Service workers require a secure context. `localhost` counts; a plain-HTTP LAN
> address does not. Some embedded browser panes block worker registration
> entirely — test in a real Chrome or a Playwright Chromium before concluding
> something is broken.
